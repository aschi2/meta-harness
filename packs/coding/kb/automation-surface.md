# Automation surface: skills, hooks, subagents, permissions, verification

What executable/config machinery a generated harness includes. Governing principle: instructions are advisory, hooks are deterministic, and the highest-value single addition is a pass/fail verification check (https://code.claude.com/docs/en/best-practices, current).

## Skills

- Create a skill when instructions are a PROCEDURE used sometimes (a checklist, a multi-step workflow, something repeatedly pasted into chat); facts and always-on conventions stay in AGENTS.md (https://code.claude.com/docs/en/skills, current). Reference material goes in skill supporting files, loaded on demand.
- The Agent Skills format (SKILL.md + optional scripts/references/assets) is an open standard (https://agentskills.io/specification, current) supported by Claude Code, Codex, Cursor, pi, Copilot, Gemini CLI, and ~40 more tools — generated skills are cross-tool assets. Placement per tool is in harness-targets.md.
- Spec essentials the generator must follow: `name` (lowercase-hyphen, matches dir name) + `description` (what it does AND when to use it, keyword-rich, key use case first — trigger reliability lives or dies on the description); body under 500 lines / ~5k tokens; file references one level deep; only the spec's six frontmatter fields are portable — Claude-specific fields (`disable-model-invocation`, `context`, `paths`, hooks) break portability, use them only in Claude-only repos.
- Side-effect workflows (deploy, release, commit) get `disable-model-invocation: true` in Claude-only repos so only the user triggers them (https://code.claude.com/docs/en/skills, current); in cross-tool repos, state the same restriction in the skill body. Autonomous: default every side-effecting skill to manual invocation in unattended runs — nobody catches a bad auto-trigger headless. Codex's analog is `allow_implicit_invocation: false` in the skill's `agents/openai.yaml` sidecar [not verified against developers.openai.com this pass].
- Scripts for deterministic operations, prose for judgment; add scripts only where they improve reliability (https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills, 2025-10-16).
- Caution: skills can fail to trigger — for always-needed knowledge prefer the AGENTS.md pointer index (see context-files.md, Vercel eval).
- Generate few skills. Candidates that earn a skill in most repos: a "run/launch the app" recipe, a deploy/release procedure, a domain workflow with 3+ non-obvious steps. Everything else starts as an AGENTS.md line [heuristic].
- **Curated skills pay, and unreviewed agent-authored ones can cost.** On SkillsBench (87 tasks, 8 domains including 16 software-engineering tasks, deterministic programmatic verifiers, 3 trials at temperature 0, 18 model×harness configurations), human-curated skills lifted macro pass rate 33.9% → 50.5% (+16.6pp, positive in every configuration, range +4.1 to +25.7pp) — though even curated skills hurt 13 of the 87 individual tasks. Letting the agent author its own skills instead landed *below* the no-skill baseline on all three configurations tested: −8.1pp (Claude Code + Opus 4.7), −11.3pp (Codex + GPT-5.5), −11.5pp (Gemini CLI + Gemini 3.1 Pro), against +18.2/+19.7/+24.8pp for curated skills on those same setups (https://arxiv.org/abs/2602.12670, 2026-06-14). Read this as support for review-before-adoption, not as a clean measurement of authorship quality: the authors state the self-generated deficit mixes content quality with skill-discovery and creator/solver interference, and that skill injection lengthens context, so part of the curated gain may be added context rather than procedural structure.
- Portable format does not mean portable performance. Skills carry across model families and can beat a model's own self-authored ones, but transfer also fails hard: skills evolved on a 4B model dropped a much stronger model from 50.5% to 18.1% on one benchmark, by encoding low-level workarounds and fragmented diagnostics the stronger model did not need (https://arxiv.org/abs/2608.27454, 2026-08-27). Inherited and marketplace skills are not free either — mean quality across a ~2M-skill ecosystem snapshot was 6.2/12 (SD 2.8) on a completeness/clarity/specificity/examples rubric, against 10.1/12 for a curated set (https://arxiv.org/abs/2602.12670, 2026-06-14). Read one before adopting it.
- Where the notes layer is generated (see memory-and-docs.md), its consolidation procedure ships with it — a `consolidate-notes` skill: read recent entries, merge duplicates, re-verify cited code locations, mark superseded entries, and propose (not apply) promotions into AGENTS.md or a skill, naming the entry behind each. This is the step that keeps a notes file from decaying into an append-only memory bank, so it is not optional there; without the notes layer, don't generate it. A pattern is promotion-worthy once it has cost something twice — the same second-occurrence rule memory entries use [heuristic].
- Do not generate the *automatic* form of that loop — rollouts scored against a validation split with edits accepted on a numeric gain [heuristic]. Published loops do beat no-skill baselines, so this is a scope judgment rather than a refutation: they inject the full skill set into the prompt and explicitly do not evaluate retrieval or triggering, which this KB already flags as where skills fail in practice (https://arxiv.org/abs/2608.27454, 2026-08-27); none evaluates repository work; and the gate is noisy — across 14 settings it selected an evolved skill in 11, of which 9 improved test performance (https://arxiv.org/abs/2608.02636, 2026-07-31). Most repos have no scored validation split to gate on at all.

## Hooks

- Use hooks for actions that must happen every time with zero exceptions; if the agent already reliably follows a written rule, delete the rule or make it a hook (https://code.claude.com/docs/en/best-practices, current).
- The proven starter set (generate only those matching the repo's actual tooling):
  1. Format-on-edit: PostToolUse on Edit|Write → run the repo's formatter on the touched file (https://code.claude.com/docs/en/plugins, current).
  2. Dangerous-command block: PreToolUse on Bash denying destructive patterns (force-push, rm -rf outside the repo, prod credentials, migrations dirs) — evaluated even under permission-bypass modes (https://code.claude.com/docs/en/hooks, current). Skip if an equivalent guard (e.g. a safety-net plugin) is already installed.
  3. Stop gate: run the cheap check suite (typecheck/lint/fast tests) on Stop, exit 2 blocks the turn ending until it passes (auto-overridden after 8 consecutive blocks) (https://code.claude.com/docs/en/best-practices, current).
- Mechanics the generator must get right: exit code 2 blocks, exit 1 does NOT; narrow matchers + `if:` conditions so hooks don't spawn processes on every tool call; explicit timeouts; `async: true` for expensive non-blocking post-hooks (https://code.claude.com/docs/en/hooks, current).
- Hooks execute arbitrary code — keep generated hooks short, readable, dependency-free shell; anything complex becomes a checked-in script the hook calls [preference].
- Stop-gate livelock: a completion gate that re-presents a checklist after the agent signals completion can loop forever (observed in agent traces: "Agent calls task_complete → sees QA checklist...infinite loop") (https://arxiv.org/abs/2603.28052, 2026-03-30) [trace-level, n=1]. A gate must be a pass/fail check, not a re-prompt.

## Path portability in emitted config

Generated config is copied to other machines — a Linux VM, a container, a teammate's laptop. A machine-absolute path silently disables whatever references it. Rules for anything the generator writes:

- Never emit a machine-absolute path (a specific home directory or package-manager prefix). Use `~` or `$HOME`, or a repo-relative path.
- Know which fields expand what, because it differs per tool and per field (all verified 2026-08-28 on codex-cli 0.147.0 / current Claude Code):
  - Claude Code hook `command` strings run through a shell, so `"$HOME"` expands — quote it: `sh -c 'bash "$HOME"/.claude/hooks/x.sh'`.
  - Claude Code marketplace `source.path` expands `~`.
  - Codex `writable_roots` expands `~` but NOT environment variables — `$HOME/.dart-tool` is silently treated as a literal and the write is denied.
- Where a toolchain lives at different paths per OS, list every candidate: non-existent `writable_roots` entries are ignored rather than erroring (verified same day), so one list can cover macOS and Linux.
- Discover, never inherit. Derive a path on the machine you are generating on (`flutter --version --machine`, `go env GOROOT`, `npm config get cache`, `which <tool>`) and write the confirmed value. Copying a path from another repo's harness, or listing plausible candidates, produces config that is right by luck.
- Machine-specific values go REPO-EXTERNAL, not into a gitignored file in the repo. A repo is shared and lives on many machines at once, so a per-machine value inside it is wrong for every machine but one; gitignoring only hides that, costs a `.gitignore` entry in shared config for a personal concern, and loses the file to `git clean -xdf` or a fresh clone. Put it in the tool's user-level config and keep the repo file to portable policy.
- The split works because tool configs merge at key level, verified 2026-08-28 on codex-cli 0.147.0: `~/.codex/config.toml` holding `[sandbox_workspace_write] writable_roots` and a repo's `.codex/config.toml` holding `[sandbox_workspace_write] network_access` both took effect — the project table did not clobber the user's array. So policy (sandbox mode, approval, network) is committed and shareable while paths stay on the machine.
- The placement is the user's call, not the generator's: writing outside the repo touches config shared with their other work, and the reasonable answers differ per person (machine-wide config, a named profile invoked with a flag, or a gitignored in-repo file). Offer the options with a recommendation and the trade-off each carries, show the exact lines, and write only what is chosen. Never place it silently. That is usually correct for toolchain paths — a Flutter SDK cache is the same for every Flutter repo on the machine — and it is exactly why the value is not repo-scoped in the first place.
- Only when a tool has no user-level layer at all does a gitignored in-repo file become the fallback, and then it is a documented compromise rather than the pattern.
- Codex specifically has no local-override file: `~/.codex/config.toml` and a project's `.codex/config.toml` merge, `[projects."<path>"]` carries only `trust_level` (not sandbox settings), and no value expands environment variables (https://learn.chatgpt.com/docs/config-file/config-reference, 2026-08-28). A Codex project config that needs absolute paths is therefore machine-local by construction.

- Codex CLI hooks reached general availability 2026-05-14 and support 12 lifecycle events (SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, SubagentStart, SubagentStop, Stop, SessionEnd, Interrupt), shipped enabled by default; async/background hooks and an `mcp_tool` handler type were added 2026-08 (https://blakecrosley.com/blog/codex-hooks-make-the-harness-real, 2026-08-28 — practitioner-sourced, not an OpenAI primary page). Schemas still don't converge across tools — for cross-tool repos, generate hooks per tool where its schema is known, and replicate must-happen gates as CI checks as a backstop (see Verification).

## Subagents

- Define a project subagent (`.claude/agents/`, checked in) only when it's coupled to the codebase and repeatedly needed: a reviewer that knows repo conventions, a test-writer for the repo's framework (https://claude.com/blog/subagents-in-claude-code, 2026-04-07). Description states trigger conditions, not capabilities.
- Delegation that verifiably helps: read-only parallel research/exploration (context isolation; Anthropic's parallel research system +90.2% over single-agent, at ~15x tokens — https://www.anthropic.com/engineering/built-multi-agent-research-system, 2025-06) and fresh-context adversarial review of a diff. Never parallel writers to shared state — conflicting implicit decisions produce incoherent results (https://cognition.com/blog/dont-build-multi-agents, 2025-06-12). The two sources agree on close read: parallelize reads, single-thread writes.
- Review-subagent prompt must scope to correctness/requirement gaps only — an open-ended "find issues" reviewer invents findings (https://code.claude.com/docs/en/best-practices, current).
- Default: generate at most one subagent (a repo-conventions reviewer) and only for repos with real review conventions to encode [heuristic].

## Permissions and sandboxing

- Committed `.claude/settings.json` = team policy; `settings.local.json` (gitignored) = personal. Evaluation: deny > ask > allow, first match wins; deny rules have no exceptions, so allowlists can be generous when deny is the safety net (https://code.claude.com/docs/en/permissions, current).
- Generate: an allowlist of the repo's verified safe read/build/test commands (test runner, linter, formatter, git status/diff), deny rules for secrets paths and Read of generated/vendored dirs (also a navigation win, see code-navigation.md). The full secrets/exfiltration checklist, allowlist sharp edges, and CI posture live in security.md — apply it whenever emitting permissions. Promote repeatedly-approved commands to allow rules over time — encode that as a maintenance note, not more upfront rules.
- Codex: repos can carry `.codex/config.toml`; secure default `sandbox_mode = "workspace-write"` + `approval_policy = "on-request"` (https://developers.openai.com/codex/concepts/sandboxing, current). Verify the current enum values against live docs at generation time — they drift between versions.
- Never generate permission-bypass settings or auto-approve-everything profiles.
- Mode split: steered — auto mode (a classifier reviews most actions instead of prompting the user) is the built-in default for interactive Pro/Max/Team sessions since 2026-08-14 (https://claude.com/blog/auto-mode-default-in-claude-code, 2026-08-07; https://code.claude.com/docs/en/permission-modes, current). Autonomous — `dontAsk` mode auto-denies anything that would otherwise prompt and is Anthropic's own answer for "locked-down CI and scripts"; `bypassPermissions`/`--dangerously-skip-permissions` only inside a container/VM/sandbox with egress locked down, and gives no protection against prompt injection (same citation). For unattended `claude -p` fan-outs, `--allowedTools` scoping is load-bearing, not optional (https://code.claude.com/docs/en/best-practices, fetched 2026-09-02). See security.md for the 2026-08-27 incident where auto mode's classifier itself blocked a kill command mid-attack — a classifier is a per-action control, not an isolation boundary.

## Verification loops

- "Give the agent a way to verify its work" is the top-ranked practice: something that produces pass/fail closes the loop; require evidence (test output, command + result), not assertions (https://code.claude.com/docs/en/best-practices, current). Verification classes ranked: rules-based (tests/typecheck/lint — most robust) > visual (screenshots for UI) > LLM-as-judge (least robust) (https://claude.com/blog/building-agents-with-the-claude-agent-sdk, 2025-09-29).
- Encode definition-of-done in this order: (1) AGENTS.md states the exact verify commands and "run before declaring done"; (2) Stop-gate hook for the cheap checks (Claude Code); (3) CI as the harness-independent backstop — headless review/checks on PR (claude -p / codex exec / Codex GitHub review integration) for teams already using CI.
- A repo without tests gets an AGENTS.md rule that new code ships with a minimal runnable check, not a generated test framework [preference].
- Mode split: steered — a prompt-level check plus in-conversation iteration is enough; a human backstops anything a missed check would have caught. Autonomous — needs a `/goal` condition or a deterministic Stop hook, which the docs call what "let[s] an unattended run finish correctly without you," plus a fresh-context adversarial review before the result is trusted; "the longer Claude works unattended, the more an independent check matters" (https://code.claude.com/docs/en/best-practices, fetched 2026-09-02). Caution from the same source: a reviewer prompted to find gaps will usually report some even when the work is sound — chasing every finding leads to over-engineering; scope reviewers to correctness/requirement gaps. Steered can triage findings by hand; autonomous can't, so the scoping matters more there.

## Distribution

- Harness pieces live in the repo (`.claude/`, `.agents/`, AGENTS.md) — versioned with the code they describe. Convert to a plugin only when sharing across repos/teams (official decision rule, https://code.claude.com/docs/en/plugins, current).
- Prefer CLI tools and skills over MCP servers for context cost; MCP only for live external services (https://code.claude.com/docs/en/best-practices, current; tool-definition overhead evidence: https://www.anthropic.com/engineering/code-execution-with-mcp, 2025-11).

## Scope note: ahead-of-time vs runtime-synthesized harnesses

Everything this KB generates is ahead-of-time (AOT): files written once and read by whatever agent shows up later. A research line argues the opposite — synthesize the harness per task at inference time. JIT-Agent trains a 27B model emitting an executable harness (memory, planning, action, capability-orchestration modules) that wraps a frozen backbone, reporting wins over fixed harnesses including Claude Code and Codex in 4 of 6 controlled backbone×benchmark cells, at 14.9–54.1% lower per-case API cost than the cheapest fixed harness in each cell (https://arxiv.org/abs/2608.25593, 2026-08-26). Its critique of the AOT assumption is fair and worth keeping in view: AOT "asks the optimization loop to precompile a broadly useful harness before seeing the exact structure of each future problem" (https://arxiv.org/abs/2608.25593, 2026-08-26).

Default: stay AOT — and the paper's own future work lands in the same place, expecting production runtimes to "retain a stable core while allowing the model to construct, revise, or replace selected harness components when the task demands it" (https://arxiv.org/abs/2608.25593, 2026-08-26). Reasons to note this rather than act on it: no software-engineering or repository benchmark appears anywhere in it, there is no ablation isolating any module or training stage, no seeds or variance accompany the main tables, and the cost of synthesizing the harness is never accounted separately from running it (https://arxiv.org/abs/2608.25593, 2026-08-26). Its abstract's "GLM-5.2 gains up to +20.2" is a same-backbone gain on one planning benchmark, not a margin over GPT-5.6. An unrelated prior work in its Table 1 is confusingly named "Meta-Harness" and is not this plugin.
