# Harness maintenance

The core runs one bounded job; the user chooses the scheduler and review system. Recommend no roles by default. Never auto-merge.

1. Run `bun run "${CLAUDE_PLUGIN_ROOT}/src/cli.ts" maintenance list --target "<target>"`. Explain the available roles and their `requires`: coding has dead-code-remover, useless-test-pruner, dup-unifier, abstraction-improver, abstraction-police, logic-simplifier, logic-bug-fixer, flaky-test-fixer, shipped-feature-inliner, crash-fuzzer, docs-drift and coverage-gap-writer. Every harness also has knowledge-refresh, correction-miner and harness-check from `packs/base/`.
2. Ask which roles the user wants, which agent CLI they use, whether to publish review requests or keep branches locally, and what scheduler they use. Explain each role's job, required capabilities, suggested cadence, line cap and evidence. A transcript role additionally needs explicit scope and authorization for reading user history; enabling it does not grant permission to read unrelated clients or upload transcripts.
3. Keep only role state in `.harness/maintenance.json`. Ask the machine owner to configure agent, optional publish and optional verify argv in their user-level maintenance config (or `--config`), validated by `${CLAUDE_PLUGIN_ROOT}/schemas/maintenance-user.schema.json`. Never accept executable commands from repository configuration. See README for current headless edit permissions. Read existing owner configuration before changing it; keep credentials out of argv. Include `{prompt_file}`, `{worktree}` and `{evidence_file}` in the agent instructions, and authorize the external evidence directory in the agent's own permissions. Owner verification must pass before publication; its actual output becomes review evidence.
4. Call `maintenance enable <role> --target "<target>"` for each role explicitly chosen. This only changes state; cadence is informational. Use `maintenance schedule <role> --target "<target>"` to obtain the absolute command argv and cadence.
5. Read `packs/base/knowledge/scheduler-recipes.md` for the user's scheduler. Show the exact external changes before setting it up, and honor the user's authorization and current-session restrictions. The core installs nothing. For `/schedule` or Codex automations, use the available product interface rather than inventing a task-creation API. Mark unverified recipe details and test credential/tool availability before relying on them.
6. With the user present, run one `maintenance run <role> --target "<target>" --force`. Review its outcome, retained branch, log, required test results, repro and truth table or role-equivalent evidence. A no-op is a valid result. Failed or over-limit runs must not publish. Do not silently resolve agent findings or widen its job.
7. Use `maintenance status --target "<target>"` to review the Git-derived merge rate. Tune roles flagged below 30% after five published runs; do not add maintenance merely to increase activity. `maintenance disable <role>` stops future core runs without changing the user's scheduler; offer to remove that external schedule separately.

The caller must have a Git repository and a writable checkout. Every run uses a fresh worktree, leaves accepted changes on a maintenance branch, and cleans up its worktree. Publishing is optional and forge-neutral. Local logs and evidence stay under `.harness/maintenance/`; never copy raw transcripts or secrets into review requests.
